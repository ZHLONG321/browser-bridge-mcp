# Browser Bridge MCP

This repository owns the standalone browser extensions, shared loopback service, MCP stdio adapter, clients, Windows native guards and browser-bridge skill. Node.js and Python implement the same HTTP client API and authenticated extension WebSocket protocol. The MCP adapter uses the official SDK and delegates to the Node client and existing guarded helpers; do not duplicate browser operations or change extension wire contracts in that adapter. Its entry point is `skills/browser-bridge/scripts/mcp/server.mjs`. Keep stdout reserved for MCP messages and use stderr for diagnostics. The shared service starts only through its explicit start tool and survives MCP disconnects.

MCP tools use explicit resource/action names, with Chromium and Firefox prefixes for protocol-specific operations. Each fixed action has its own tool and action-specific schema; the adapter supplies the existing HTTP action internally. Keep profile/privacy/window selection explicit and preserve raw JavaScript, CDP and native API/packet capabilities. Tool names and their mapping belong in `skills/browser-bridge/references/mcp.md`; client functions and the HTTP protocol retain their existing names.

Keep profile and privacy selection explicit on every browser call. Resolve all user-supplied target conditions against live candidates. Preserve window constraints and ask about ambiguity rather than selecting the first match. Do not introduce persistent current/default target state.

Discover available browsers before asking the user to choose. A single available browser or a target uniquely resolved from the user's conditions is sufficient for automatic selection. Distinguish Chromium browser products using process identity or candidate-page metadata when needed. Multiple profiles of one browser require target resolution, not another browser-choice prompt.

Extension setup is required only in a profile necessary for the user task. Do not request installation in unrelated physical profiles. Live discovery searches connected profiles only; an absent connection does not prove missing installation, and a password/sign-in page from another profile is not the task result. Resolve the intended profile before asking for setup. The read-only Windows Edge `edge_profile_extension_status` helper/MCP tool inspects one explicit task-required physical profile and privacy context; its saved registration evidence is separate from live state, and unknown/read errors never establish missing installation. See the task-required setup reference.

Background operation is the default without repeated user-facing announcements. Foreground interaction requires explicit user authorization, after which Windows commands can perform it; do not ask the user to keep a page visible then return to Codex. Windows native guard source and bundled x64 DLLs belong together; rebuild the affected DLL when changing its source. Refer to `skills/browser-bridge/references/windows.md` for the compiler commands and activation guards.

The skill ships two independent implementations of the same 15 Windows desktop operations: `scripts/node/desktop.mjs` uses Koffi/sharp without Python, and `scripts/python/browser_bridge_windows` uses ctypes/Pillow without Node. Neither depends on BO, another skill, the HTTP service or an extension. MCP registers 15 dedicated Node-backed `windows_*` tools. The BAT dispatches `windows` to Node or `windows-python` to uv/Python 3.12+ before checking curl; Python uses the separately pinned `scripts/python/windows-requirements.txt`, prepared explicitly and resolved offline during operations. CLI/MCP use bounded hidden per-call workers; no automatic replay or cross-runtime fallback for uncertain mutations. Process-local handles require direct composition in one owning Node or Python process. Native HWND/PID discovery does not establish Bridge profile/privacy selection. Without separate user authorization, WinAPI may act only on browsers and programs/windows directly related to the task; mode labels are not a sandbox. Captures follow the existing verified-filename/session-directory policy. Keep optional prebuilt npm dependencies enabled. Existing guarded browser startup helpers still retain their Python/native prerequisites. See `references/windows-desktop.md` inside the skill.

Chromium `debugging` supports read-only status and an authorized enable operation for an exact tab. Both server runtimes validate the same target, privacy, window and mutation contracts. The saved profile-wide enabled preference is separate from actual owned attachments. UI connection labels use live target checks, not the preference alone. A manual off/banner cancellation stops reconnection; enabling through a later authorized task is explicit. See `skills/browser-bridge/references/operations.md` for result and failure semantics.

HTTP clients use standard libraries. Extension WebSocket framing uses pinned `ws` for Node and `wsproto`/`h11` for the Python fallback; do not reimplement RFC 6455 framing. Preparation and optional Windows Edge profile dependencies are documented in `skills/browser-bridge/references/setup.md`. Keep browser profiles, credentials, connection state and generated artifacts out of Git. Temporary work belongs in `tmp/<session-id>/`.

Screenshot tools delegate to the Node client's file-producing helper using existing CDP/WebExtension operations. Keep the caller session ID explicit and save images to the caller's `%TMP%/codex-<session-id>-browser-bridge/screen/`. Encode every image without automatic downscaling or a file-size cap; return only the filename after verifying the complete nonempty file exists. Exempt only Chromium screenshot image results from ordinary CDP text truncation. Screenshot tools do not search or scroll; AI-authored saved scripts handle page-specific readiness, scrolling and stitching, restoring scroll positions in `finally`. See the screenshot reference for coordinate and encoding contracts.

Native page recording uses the Node client's per-job detached worker and existing CDP operations. Repeat caller session/profile/privacy/window/tab selection for start/status/stop/result; job state never selects a current browser. Detect native support from actual responses, preserve other failures, stop once, copy original video bytes to the caller's temporary `video/` directory, and return only a verified complete filename. Keep duration/manual stop explicit. Optional Codex notification targets a known existing loopback App Server and loaded caller thread; do not launch or resume another Codex host for it. Notification failure preserves the video. See `skills/browser-bridge/references/recording.md`.

The installed browser-bridge skill is a separate copy from this checkout. Repository changes do not automatically update an installed skill, reload extensions or restart a running service. Explain the applicable reload or installation step when changing those components.

Chromium 1.2.0 and Firefox 1.3.0 declare broad desktop browser permissions and all-URL host access at installation/update. Exclude `browsingData`; do not clear browser data through alternate APIs as setup/recovery/cleanup. Browser grants never replace task authorization. Private browsing, Chromium file/site access, native user-script controls and capture prompts remain browser-managed consent gates; request only the one actually needed in the task-required profile, with the exact browser menu/control. Do not add unsupported, ChromeOS-only or enterprise-policy-only privileges to ordinary desktop manifests. See the permission/consent section of the setup reference.

The service is shared across clients and Codex sessions. Reuse it rather than restarting it per session. Extension transport protocol 2 uses a direct service-worker/background WebSocket; HTTP polling and offscreen forwarding are inactive. `extension/socket-client.js` owns the transport implementation; run `node scripts/build-extension-transport.mjs` after editing it to package the Firefox copy. Follow the task identity, acknowledgement and reconnection contract in `skills/browser-bridge/references/operations.md`. Empty discovery during reconnection requires bounded read-only rechecks before requesting an extension reload; see the setup reference.

WebSocket protocol 2 is packaged as Chromium 1.2.0, Firefox 1.3.0 and MCP 2.4.2. Since extension 1.1.1/1.2.1, fresh inventory is published before completed results, including concurrent completions during inventory collection. Copying source or installing skill files does not replace the shared process or loaded extensions. Coordinate a shared service restart when updating its code; extension updates require one reload. A new client session requires neither. Do not claim browser reconnection has been observed from source inspection or static checks.

Node Windows entry points and guarded Windows browser helpers use `windows-platform.mjs`; the independent Python implementation uses its own `_platform.py` guard. Non-Windows calls report `WINDOWS_UNAVAILABLE` with the actual platform before native workers/libraries, Windows paths, screenshot output or WinAPI documentation requests; unrelated browser tools remain available. Do not suggest reloads or dependency installation to fix platform unavailability.
