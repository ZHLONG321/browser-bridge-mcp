# Setup and connection

For MCP installation, dependencies and client registration, read [MCP installation and tools](mcp.md). MCP needs Node.js 20.9+/npm and exposes tools over stdio. Its explicit `bridge_service_start` tool starts or reuses the shared service described below; it does not load extensions or grant browser permissions. The service accepts HTTP client requests and authenticated extension WebSockets on the same loopback port. Independent [Windows desktop commands](windows-desktop.md) ship both Node and Python implementations. Node uses prebuilt optional npm dependencies without Python; Python uses ctypes/Pillow and its own pinned requirements without Node. Neither requires curl, the service or an extension. Prepare the chosen implementation as documented in that reference. The older guarded browser-creation helpers retain their own Python/native prerequisites.

## Runtime and server

The Windows server launcher prefers Node.js 20+ with the locked `ws` dependency installed by the MCP installation command. Its fallback uses `uv`, Python 3.10+ and the pinned `scripts/python/requirements.txt` dependencies (`wsproto` and `h11`). HTTP clients themselves remain standard-library only. Install a current runtime from [Node.js](https://nodejs.org/en/download) or [Python](https://www.python.org/downloads/windows/), or provide a portable runtime on PATH. Reopen the terminal after changing PATH. The launcher uses offline Python resolution, never downloads a runtime, and never runs an online package installer.

Prepare the Python fallback explicitly from the skill directory with network access authorized for dependency installation:

```sh
uv run --no-project --python ">=3.10" --with-requirements scripts/python/requirements.txt python --version
```

Run the prepared server with the same command plus `--offline`, replacing `python --version` with `python -B scripts/python/server.py --session <session-id>`. Either server works with both HTTP clients and extensions. WebSocket framing uses [ws](https://github.com/websockets/ws) or [wsproto](https://python-hyper.org/projects/wsproto/en/stable/) rather than a custom RFC implementation.

```bat
scripts\browser-bridge-server.bat --session <session-id> --port 30003
scripts\browser-bridge.bat status
scripts\browser-bridge.bat stop
```

`--session` is required. Logs go to `%TMP%/<session-id>/browser bridge/server.log`; the launcher reports its path and whether the service started. A server already occupying the requested port is reported, never killed or silently replaced. `stop` requests shutdown of the Bridge at the configured URL; use only for the service you intend to stop. There is no cwd initialization.

The HTTP commands in the client BAT require curl with `--fail-with-body` support (7.76+); the separate `windows` and `windows-python` commands do not. Windows 10/11 generally supplies curl. If unavailable, tell the user to install/update it from [curl for Windows](https://curl.se/windows/) and expose `curl.exe` on PATH. Do not bundle executables or download them automatically.

## Connection recovery

The HTTP service is shared by clients and Codex sessions. Reuse a compatible running service; a new session does not need a fresh service or a browser/extension restart. Stopping it interrupts other callers. Server updates require one coordinated restart, not a restart on every client connection.

If discovery is empty or a call reports `PROFILE_NOT_CONNECTED`:

1. Check `bridge_service_status` or the CLI `status`. If the service is unavailable, start it with `bridge_service_start` or the documented launcher, then discover again. Do not kill or replace a service already using the port.
2. Allow automatic extension reconnection before requesting user intervention. Repeat read-only MCP `browser_profile_list`/`browser_connection_list` or CLI `profiles`/`discover` roughly every two seconds for up to 60 seconds; stop as soon as the required connection appears. This allows the WebSocket heartbeat timeout, retry and bootstrap exchange described in [Operations](operations.md#jobs-websockets-and-reconnection). One empty response establishes only the current observation. A connected profile with no matching page is a target lookup problem, not a disconnected extension.
3. Resolve the original browser/profile/privacy/window conditions against fresh inventory; never substitute another profile. Use `browser_job_status` or `job_status` for an uncertain request's job ID and exact original selection. Follow the [job recovery contract](operations.md#jobs-websockets-and-reconnection) before deciding on another operation.
4. If still disconnected, inspect running browser processes and report the actual service error and available connections. Follow [Task-required profile setup](#task-required-profile-setup); only the profile needed for the task may require installation or permissions. Reload is appropriate for a newly installed extension version or a persistent extension failure, not as the first response to an empty inventory. Debugging being off does not prevent inventory connections; an enabled preference without a debugger attachment is also separate from transport health.

Both extensions bootstrap a fresh secret and reconnect automatically after the local service returns. Transport recovery does not restart browser operations. Service shutdown disconnects its extension sockets and waiting HTTP clients, so connections cannot remain attached to a retired listener. Browser/extension execution-context restarts have different task-result semantics; see [Operations](operations.md#jobs-websockets-and-reconnection).

WebSocket protocol 2 requires Chromium extension **1.1.0+**, Firefox extension **1.2.0+** and service/MCP **2.3.0+**. Chromium requires Chrome/Edge 116+ for service-worker WebSocket lifetime support. For an upgrade, install the locked dependencies, coordinate one shared service restart, reload each updated extension once and reconnect MCP to discover the updated tools. Source edits do not replace loaded components. `SERVICE_UPGRADE_REQUIRED` identifies an old service; `EXTENSION_UPGRADE_REQUIRED` identifies an old extension transport. Ordinary reconnection does not require repeated extension reloads.

## Extension

Chrome/Edge use `extension/`; Firefox uses `extension-firefox/`. Both use authenticated WebSockets to either service runtime, configured using its loopback HTTP origin. Neither discovers browser executable paths or starts a browser. Copy the whole skill directory to another computer, prepare the documented runtime dependencies/curl, then load the appropriate extension in each intended profile; no workstation path is embedded in the package.

1. Resolve this skill's `extension/` directory to an existing absolute path first. Open `chrome://extensions` or `edge://extensions`, enable Developer mode, and choose **Load unpacked** using that computed path. On Windows the usual root is `%USERPROFILE%/.agents/skills/browser-bridge`, but expand it before giving the picker input.
2. Load only in a profile needed for the user's task, if it is not already installed there. Other profiles need no installation. Open extension options and set its service URL. No profile/account labels or default target are stored; every operation supplies its own profile and privacy context.
3. JS, frame, CDP and userscript operations need debugging. Either use **Enable debugging** in extension controls or let the agent call the authorized `debugging` enable operation for the resolved target. Listing profiles/tabs and querying debugging status work while debugging is off. The saved switch is separate from actual connections: the UI shows enabled/waiting after a restart until a page connects, and connected counts only for this extension's tracked sessions. No off/on cycle is required for an ordinary restart; page operations attach when needed.
4. For private windows, explicitly enable **Allow in Incognito / Allow in InPrivate** on the extension's Details page. The extension uses spanning mode and reports each tab/window's privacy state separately.
5. Run `profiles`, select the appropriate profile, then enumerate its `normal` or `private` tabs. No result means no currently visible connection/window, not proof that the profile or account does not exist.

For Firefox, resolve this skill's `extension-firefox/manifest.json` to an existing absolute path, then provide that computed file path for **about:debugging → This Firefox → Load Temporary Add-on**. Accept Firefox's installation/update permission approval when shown, then set the service URL and enable native control in Options. Desktop API and website permissions are declared at installation, not selected in a separate optional-permission checklist. Allow private browsing in the add-on's details only when needed. Temporary installation ends on browser restart; permanent installation on release Firefox requires Mozilla signing. See [Firefox](firefox.md) for native calls, [Window operations](windows.md) for guarded Windows background creation and signing options, and [RDP](rdp.md) only when native debugger actors are needed. An extension connection alone does not require RDP setup or its confirmation dialog.

Do not disable another installed extension or restart a user's browser to repair a connection without authorization. If an older Bridge extension attaches a debugger to the same tab, explain the conflict and ask the user which extension should control it.

Server script changes require restarting the server; client/helper script changes load on the next new invocation. Extension changes require **Reload** on the extension card (Chromium) or `about:debugging` (Firefox); a service URL change reconnects automatically. Installing a new skill may require refreshing skill discovery in an existing agent session. Existing Chromium calls remain compatible; Firefox adds `discover`, `webextension` and `rdp` rather than changing Chromium method semantics.

Sources: [Chrome service-worker WebSocket lifetime](https://developer.chrome.com/docs/extensions/how-to/web-platform/websockets), [Chrome incognito modes](https://developer.chrome.com/docs/extensions/reference/manifest/incognito), [Edge extension access](https://support.microsoft.com/en-us/edge/change-site-access-permissions-for-extensions-in-microsoft-edge), [Node hidden subprocesses](https://nodejs.org/api/child_process.html), [curl HTTP/file requests](https://curl.se/docs/manpage.html).


Before giving Windows picker instructions, resolve the extension directory or Firefox manifest file using the actual user skill root and verify it exists. Give the resulting absolute filesystem path, not a relative path or an unexpanded `%USERPROFILE%` expression. For example, compute it with `Path(os.environ["USERPROFILE"]) / ".agents/skills/browser-bridge/extension-firefox/manifest.json"` and `.resolve()`, or use this skill's already resolved location. The directory/file distinction matters: Chrome/Edge picks a directory, Firefox picks `manifest.json`.

## Task-required profile setup

Only a profile required by the user's task needs Bridge installation. The existence of other physical profiles, even running ones, does not justify asking the user to install into them. Live Bridge discovery lists connected profiles only; finding one profile does not establish that all relevant profiles were searched. An absent connection is not evidence of missing installation.

First resolve the task target using all supplied conditions and available task-related metadata. If the connected candidates do not identify it, including when the user disputes a found password/sign-in page, explain the incomplete search coverage. Ask which browser profile contains the target only when available evidence cannot resolve it. Do not ask for a site password based on another profile's page, switch to a default profile, create a replacement page, or require installation in every profile. For a new task with no existing target, the browser's freshly resolved startup profile is the task-required profile.

On Windows Edge, `edge_startup_profile_get` or Node `edge_defaults()` supplies registered physical profile names and the user-data directory. This saved inventory does not prove a profile is running or contains the requested page. After resolving one necessary physical profile, call MCP `edge_profile_extension_status({user_data_dir, profile_directory, context})`, or import that same function from `scripts/node/windows.mjs` in a saved script. The physical directory (such as `Profile 4`) is not a Bridge UUID. The check reads only that profile's saved extension registry and launches nothing; it does not require the optional LevelDB parser or a running Bridge service.

| Evidence for the task-required profile | What to tell the user |
| --- | --- |
| Live connection satisfies all conditions | Continue the task; do not request setup in other profiles. |
| `registration: present`, but the needed connection is unavailable | Installation is registered. Follow connection recovery and report actual errors; do not request reinstallation. Registration alone does not prove the extension is enabled. |
| Private task and live private access is denied | Ask to allow private browsing for this profile's extension. A saved `private_allowed: false` is a clue to check, not proof of current permission state. Do not reinstall or substitute a normal window. |
| `registration: not_found` | State that this skill's extension was not found in this profile's saved registry. If it is still missing in that profile, ask the user to load it there, naming the profile and supplying the returned existing absolute `extension_path`. Other profiles need no installation. |
| `registration: unknown`, a read error, conflicting live evidence, or uncertain profile association | State what could not be established and request only the missing distinction/check. Do not claim the extension is uninstalled or request duplicate installation. |

The check's `evidence: saved_preferences` can lag the live browser. `connection_state: not_checked` deliberately makes no connection claim. `not_found` concerns this installed skill copy; a saved registration with the Browser Bridge manifest name under another path yields `unknown` rather than a duplicate-install instruction. Read failures preserve their actual errors and must never become `not_found`. The helper does not inspect disconnected pages or account credentials. For other browsers, use available read-only evidence or ask the user to check the identified profile; absence from Bridge alone never establishes missing installation.

An installation prompt must name the necessary browser/profile, explain the evidence, and provide the computed absolute picker path. For example: "The requested page is in Edge profile <name> (<physical directory>), which is not connected. Its saved registry has no registration for this skill extension. If Browser Bridge is absent in that profile's extension manager, choose Load unpacked there using <existing absolute extension directory>. The connected profile needs no changes." After setup, discover again and resolve the original URL/title/privacy/window conditions before operating; do not treat installation as selection of a persistent default.

## Browser permissions and manual consent

Chromium 1.2.0 and Firefox 1.3.0 declare broad desktop API permissions and `<all_urls>` at installation/update. Chromium's shared package targets desktop Edge/Chrome APIs; Firefox uses its supported MV2 APIs, including legacy `user_scripts`. Browser-specific or newer APIs still depend on the actual browser/version. ChromeOS-only, enterprise-policy-only and development-channel-only privileges are not enabled by this package. For example, ordinary Chromium MV3 extensions cannot gain `webRequestBlocking` by adding it to the manifest; use the supported CDP or declarative network APIs. Chrome-only APIs not supported by Edge, such as Reading List and GCM, are outside the shared package. Permissions do not add MCP tools or implement a missing browser API.

`browsingData` is deliberately absent from both manifests. Do not request it or clear browsing data through Cookie, History, CDP, storage or OS operations as a setup/repair/cleanup workaround. Broad permissions authorize no unrelated reads, browser-setting changes, account access or destructive actions. Chromium's `background` permission can extend browser lifetime and startup behavior; it does not promise continuous execution and is not a reason to change the user's system/browser settings.

After installing these versions, ask the user to reload the affected extension once and approve any permission-update prompt shown by that browser. A saved file/version is not evidence that the loaded extension has changed or that permission was granted. Do not require reloading an unchanged extension on every task. Firefox Options shows actual `permissions.getAll()` results and `private_allowed`; its native `permissions.getAll` call is also available through the resolved WebExtension connection.

For later tasks, ask for manual consent **only when the needed operation is blocked by that specific gate**. Preserve the native error and check the actual browser/product/version, task-required profile, privacy context and target. A missing namespace may mean an unsupported API/version, not denied permission; a connection timeout is not a permission diagnosis. Read available grant/access status before asking. An extension disconnected from a profile does not establish a missing permission.

Give one concrete instruction naming the browser, physical profile when known, Browser Bridge extension and required control. Use the matching row below; translate the labels into the user's language. Use the live extension ID in a details-page URL only when it is actually known. Do not guess IDs or label paths, switch to another profile/privacy context, automatically open/focus settings, click approval for the user, change protected preferences or disable browser safeguards. If the control is absent, check browser/API support or policy instead of inventing a button. Continue independent work while the affected operation waits; after the user confirms, rediscover the original target and check access before resuming. Preserve uncertain mutation/job results rather than blindly replaying the failed operation.

| Actual gate | Tell the user where to click |
| --- | --- |
| Edge private-window access denied | In the required Edge profile, open `edge://extensions` → **Browser Bridge → Details → Allow in InPrivate**. |
| Chrome private-window access denied | In the required Chrome profile, open `chrome://extensions` → **Browser Bridge → Details → Allow in Incognito**. |
| Firefox private-window access denied | In the required Firefox profile, open `about:addons` → **Extensions → Firefox Browser Bridge → Details → Run in Private Windows → Allow**. |
| Chromium local `file:` access denied | Use that browser's extension manager above → **Browser Bridge → Details → Allow access to file URLs**, when offered. Do not give Firefox a Chromium-only switch; use Firefox's actual access/error and supported API. |
| Chromium website access withheld | Extension manager → **Browser Bridge → Details → Site access**; permit the task's site. If the user explicitly wants all sites, choose **On all sites**. This changes site access, not private/file access. |
| Native Chromium `userScripts` API blocked by its user toggle | Chrome 138+ uses **Browser Bridge → Details → Allow User Scripts**; Chrome 120–137 uses **Developer mode** on `chrome://extensions`. On Edge use `edge://extensions` and the corresponding control actually offered by that version. This concerns native `chrome.userScripts`, not Bridge's existing CDP-backed userscript operation. |
| Firefox native control disabled | `about:addons` → **Extensions → Firefox Browser Bridge → Preferences/Options** → check **Enable native browser control → Save**. An enabled switch with an unrelated API failure does not require off/on. |
| Native capture requires user invocation or a share picker | Explain the exact native capture route first. `tabCapture` requires the user to invoke the extension; `desktopCapture` presents a picker where the user selects the intended tab/window/screen and confirms **Share**. Permission declarations do not bypass those steps. Do not promise an extension button implements a recording action that is absent. Use the existing background recording route when it supports the task; a missing native recording capability is `unsupported`, not a reason to request arbitrary permissions. |
| Website camera/microphone/location permission denied | For the task's site, use the browser's address-bar **Site information/Permissions** control and permit only the required device/capability, then let the user accept any actual browser/OS prompt. Extension permissions alone do not establish a website's grants. |
| Native messaging host missing | Report the named host and missing installation/registration prerequisite. `nativeMessaging` permission does not install a host; there is no extension-details toggle that repairs it. Obtain authorization before installing or registering software. |

Manual consent is a settings/picker interaction, not a screenshot workaround: never ask the user to keep a task page/browser in front while returning to Codex. `<all_urls>` does not unlock every internal/protected page, make inactive-tab `captureVisibleTab` possible or prove that a PDF has rendered. Background operation remains the default after consent; a separately authorized foreground task can use the Windows commands.

## Optional Windows Edge profile association

The guarded Edge window helper needs `uv`, Python, the architecture-matching native guard, and Google's `dfindexeddb` parser to read this Bridge extension's stored profile UUID in the explicitly selected physical profile. It does not inspect website credentials or other extensions' storage. Prepare the pinned dependency explicitly before calling the helper:

```bat
uv run --no-project --with "dfindexeddb @ https://github.com/google/dfindexeddb/archive/b65ff9bd6dedb61e7b288e1bdadf68ef6b1f56bb.zip" python -c "import dfindexeddb"
```

The helper uses `--offline` and never downloads that dependency during browser operation. Missing dependencies stop with the runner's error. The source pin uses upstream's relaxed Snappy dependency for newer Python versions; the published `20260210` package pins an older Snappy release with limited Windows wheel availability. See the upstream [parser and installation documentation](https://github.com/google/dfindexeddb) and [pinned dependency definition](https://github.com/google/dfindexeddb/blob/b65ff9bd6dedb61e7b288e1bdadf68ef6b1f56bb/pyproject.toml).

Keep `scripts/windows/foreground-guard.dll` and `edge-startup-guard.dll` beside their included source files and Python helpers. The bundled native components target x64; fully exited Edge startup also checks for 64-bit Python and x64 Edge before launch. It uses a process-scoped startup callback to open ordinary or InPrivate windows without minimizing or changing browser settings. Existing Edge processes use the thread guard and extension API. See [Windows operations](windows.md) for the method and compiler commands. Client/helper and native-component changes load on the next new call; these changes alone do not require an extension reload.
